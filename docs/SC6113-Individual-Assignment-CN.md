## 1. 引言（Introduction）

区块链可以将资产管理规则写成公开、可验证且自动执行的智能合约。在传统 Web 应用中，支付平台既维护数据库，也决定何时付款；而在 DApp 中，用户使用自己的钱包签名交易，资金规则由部署在区块链上的程序执行。因此，区块链特别适合处理参与方缺少直接信任、但业务条件能够形式化表达的金融场景。

本项目选择自由职业付款作为应用场景，并将普通的一次性托管扩展为里程碑托管。相比“完成全部工作后一次付款”，里程碑模式能够降低双方风险：客户可以逐阶段验收，自由职业者也能逐阶段取得收入。系统的功能范围集中于资金锁定、条件式释放、争议处理和交易审计，不涉及人才匹配、即时通信与信誉评价等综合平台功能。

## 2. 问题陈述（Problem Statement）

远程和跨境自由职业项目中，客户与自由职业者可能互不认识，且双方难以低成本追责。直接预付款会使客户承担未交付风险；完成后付款则使自由职业者承担拒付风险。中心化平台虽然提供托管，但用户必须相信平台正确保管资金、执行规则且不会单方面限制账户。

本项目要解决的核心问题是：**如何在不把项目资金交给单一平台控制的前提下，使客户和自由职业者按照事先约定的里程碑完成条件式付款，并在发生争议时保留透明、可追踪的处理路径。**

系统边界定义如下：交易资产限定为 Sepolia 测试 ETH，不涉及法币清算；项目资金在开始时一次性全额存入，每个里程碑独立结算；每个项目由客户在创建时指定一名双方认可的仲裁者；链下数据库仅保存元数据与查询索引，不替代智能合约中的资金状态。

## 3. 项目目标（Objectives）

本项目的目标如下：

1. 建立透明且可验证的里程碑托管机制，使客户资金由智能合约保管，并根据交付或裁决结果释放或退回。
2. 为 Client、Freelancer 和 Arbitrator 提供清晰的角色权限与状态转换规则，防止未授权操作和重复付款。
3. 提供完整的 DApp 交易体验，使用户能够通过 MetaMask 完成项目创建、资金存入、里程碑处理、争议解决及交易状态查询。
4. 明确划分链上与链下职责：智能合约保存资金和业务状态，Flask 与 SQLite 保存项目元数据、状态镜像和交易索引。
5. 提供适用于桌面浏览器和 MetaMask 移动端内置浏览器的界面，并通过输入验证、操作确认和错误提示降低误操作风险。
6. 验证系统的主要业务流程及异常操作处理，并评估其在安全性、可用性、性能和数据一致性方面的限制。

## 4. 系统架构（System Architecture）

### 4.1 功能架构

系统功能围绕托管项目的生命周期组织，并由 Client、Freelancer 和 Arbitrator 三种角色共同参与。钱包连接为所有业务功能提供身份和签名能力，项目与里程碑模块负责正常履约流程，争议仲裁和超时退款处理异常情况，查询模块则向用户呈现项目状态和交易记录。

| 模块 | 主要功能 | 参与角色 |
|---|---|---|
| 钱包与身份 | 连接 MetaMask、恢复授权、切换账户与网络、显示地址和余额 | 所有角色 |
| 托管项目 | 创建项目、指定 Freelancer 与 Arbitrator、设置截止日期和里程碑、存入资金 | Client |
| 里程碑处理 | 提交交付结果、批准里程碑、释放阶段资金、截止日后退款 | Client、Freelancer |
| 争议与仲裁 | 对已提交里程碑发起争议，由项目指定仲裁者决定放款或退款 | Client、Freelancer、Arbitrator |
| 项目查询 | 按角色查看 Dashboard、项目详情、资金进度、里程碑状态和可用操作 | 所有角色 |
| 交易与同步 | 保存项目元数据、同步已确认交易、筛选交易历史并跳转 Etherscan | 所有角色、系统后端 |

各模块共享输入验证、操作确认、错误反馈和响应式布局。用户可执行的操作由其钱包地址、项目角色和当前业务状态共同决定；前端只展示符合条件的操作入口，智能合约负责最终权限验证。

系统采用前端、后端、区块链和数据库相互协作的混合架构：

该架构遵循“链上金融真相、链下应用数据”的原则：

- 智能合约负责资金、角色权限、托管状态和里程碑状态，是最终可信来源。
- Flask 不保管私钥，也不代表用户发起金融交易；它负责验证和保存前端提交的链下数据。
- React 前端协调两条数据路径：通过 MetaMask 调用合约，通过 REST API 读取或同步应用数据。
- SQLite 保存项目标题、描述和交易历史等便于检索的数据，以降低每次页面加载都遍历链上日志的成本。

### 4.3 交易数据流

以客户批准里程碑为例：客户在详情页点击“Approve & Release”，前端先显示确认对话框，再通过 Ethers.js 调用 `approveMilestone()`。MetaMask 展示交易和 gas 信息，用户签名后交易被广播到 Sepolia。前端等待交易回执；确认成功后，将交易哈希、区块号、项目编号和操作类型提交到 Flask。后端新增交易记录，并把对应里程碑镜像状态更新为 `RELEASED`。最后前端重新加载详情。即使链下同步失败，链上资金结果仍然有效，页面会以警告提示用户同步异常。

## 6. 智能合约设计（Smart Contract Design）

### 6.1 数据模型与状态机

`FreelanceEscrow.sol` 是系统唯一的主合约。每个 `Escrow` 保存客户、自由职业者、该项目仲裁者、总金额、已入金金额、截止时间和项目状态；每个 `Milestone` 保存序号、说明、金额、状态以及提交和批准时间。项目与里程碑分别采用以下状态：

```text
Escrow: CREATED ──fund──> FUNDED ──全部里程碑终结──> COMPLETED / CANCELLED

Milestone: PENDING ──submit──> SUBMITTED ──approve──> RELEASED
                                      │
                                      └──dispute──> DISPUTED
                                                        ├──release──> RELEASED
                                                        └──refund───> REFUNDED

PENDING ──deadline passed + client refund──> REFUNDED
```

其中 `RELEASED` 和 `REFUNDED` 是不可再次处理的终态，可防止重复放款。所有里程碑进入终态后，合约根据结果把项目标记为 `COMPLETED` 或 `CANCELLED`。

### 6.2 核心函数

| 函数 | 调用者 | 主要规则与结果 |
|---|---|---|
| `createEscrow` | Client | 三方地址必须不同；截止日期在未来；至少一个里程碑；每笔金额大于零 |
| `fundEscrow` | Client | 仅 `CREATED` 状态可调用；`msg.value` 必须精确等于项目总额 |
| `submitMilestone` | Freelancer | 项目必须已入金，里程碑必须为 `PENDING` |
| `approveMilestone` | Client | 仅批准 `SUBMITTED` 项；状态先更新，再向 Freelancer 转账 |
| `raiseDispute` | Client/Freelancer | 仅双方可对 `SUBMITTED` 项发起争议 |
| `resolveDispute` | 本项目 Arbitrator | 决定放款给 Freelancer 或退款给 Client |
| `refund` | Client | 截止日后，可退回仍为 `PENDING` 的里程碑资金 |

每个关键操作都会触发事件，例如 `EscrowCreated`、`EscrowFunded`、`MilestoneSubmitted`、`MilestoneApproved`、`DisputeRaised`、`DisputeResolved` 和 `Refunded`。事件既便于 Etherscan 审计，也为独立链上索引器提供标准化数据来源。

### 6.3 安全设计

- **授权控制：** `onlyClient`、`onlyFreelancer` 和仲裁者地址检查限制不同角色的权限，前端隐藏按钮只改善体验，最终授权仍由合约执行。
- **输入验证：** 合约拒绝零地址、自我交易、重复角色、过期截止日、空里程碑、空描述和零金额。
- **防止重复付款：** 放款只能从 `SUBMITTED` 或 `DISPUTED` 状态进入终态，之后相同调用会回滚。
- **重入风险控制：** 转账采用 Checks-Effects-Interactions 顺序，在外部 `call` 之前更新状态；若 ETH 转账失败，`require` 使整个交易回滚。
- **私钥保护：** 合约调用由 MetaMask 在用户设备中签名，前端和后端均不读取或保存私钥。
- **误转账保护：** `receive()` 会回滚直接转入的 ETH，用户只能通过 `fundEscrow()` 入金。
- **整数安全：** Solidity 0.8 提供溢出检查；前后端金额均以 wei 的整数/数字字符串传递，避免 JavaScript 浮点误差。

在 gas 方面，合约使用单一主合约和映射索引，查询函数为 `view`；但创建项目时需要循环写入里程碑及其字符串描述，因此里程碑数量和描述长度会提高单次创建成本。该成本特征构成当前实现的主要性能约束。

## 7. 应用设计（Application Design）

### 7.1 前端页面与交互

前端采用四个主要页面：

1. **Dashboard：** 根据当前钱包将项目分为 Client、Freelancer 和 Arbitrator 三种视角，展示活跃项目、锁定资金、待处理事项和完成数量。桌面端使用分段选择器，移动端使用全宽下拉框。
2. **Create Escrow：** 使用三步式表单依次收集参与方、项目资料、截止日期和里程碑。页面验证 Ethereum 地址、角色冲突、未来日期、描述长度和最多六位小数的正数金额，并使用 `parseEther()` 以 wei 求和。
3. **Escrow Detail：** 展示三方地址、资金进度和里程碑状态，并按当前角色和状态动态显示 Fund、Submit、Approve、Dispute、Resolve 或 Refund。所有不可逆操作均有二次确认。
4. **Transaction History：** 按时间倒序展示交易，支持项目、操作类型、状态和分页筛选；交易哈希和区块号可跳转到 Sepolia Etherscan。

为了适配主要使用场景——MetaMask 移动端内置浏览器——界面在小屏幕下采用固定底部导航、较窄顶部栏、至少 44 px 的关键触控区域、单列操作按钮和卡片式交易历史。桌面端则使用左侧导航和表格。地址会缩写显示并提供复制及区块浏览器链接；长标题、金额和地址均设置了换行或溢出策略。

### 7.2 后端 API 与数据库

Flask 使用应用工厂模式并在 `/api` 下注册蓝图。主要接口如下：

| Method | Endpoint | 功能 |
|---|---|---|
| GET | `/api/escrows` | 按地址、角色、状态查询项目并分页 |
| GET | `/api/escrows/<id>` | 返回项目详情与里程碑 |
| POST | `/api/escrows` | 链上创建确认后保存元数据 |
| GET | `/api/transactions` | 按项目、地址、动作和状态查询交易历史 |
| POST | `/api/transactions` | 保存已确认交易并更新链下状态镜像 |

数据库包括 `escrows`、`milestones` 和 `transactions` 三张表。Ethereum 地址统一转为小写以便查询；金额以最长 78 位的字符串存储；`escrow_id + milestone_index` 和 `tx_hash` 分别具有唯一约束。后端再次校验地址、交易哈希、金额、日期、里程碑顺序和金额总和，错误响应包含稳定的错误码与 HTTP 状态码。

## 8. 实现（Implementation）

### 8.1 钱包与链上调用

应用通过 EIP-1193 Provider 检测 MetaMask。首次连接使用 `eth_requestAccounts`，刷新页面使用 `eth_accounts` 静默恢复授权，并监听 `accountsChanged` 和 `chainChanged` 事件。全局 `WalletContext` 保存地址、网络、余额、Provider 和 Signer。用户发起写操作时，通用交易函数依次完成“请求签名—返回交易哈希—等待回执—取得区块号”，界面则用 Mantine Notifications 展示对应的等待、已提交、成功或失败状态。

创建项目时，前端从 `EscrowCreated` 日志解析链上 `escrowId`，再调用后端保存标题、项目描述和里程碑镜像。其他操作在回执确认后调用 `/api/transactions`，后端依据 `action` 更新镜像状态。这种顺序避免了链下数据库先显示成功、链上交易随后失败的情况。

### 8.2 数据一致性和错误处理

系统明确区分链上成功与链下同步成功。创建交易已确认但交易历史保存失败时，前端仍报告“Escrow 已在链上创建”，同时给出同步警告。后端使用唯一交易哈希防止重复上报，并仅让 `CONFIRMED` 记录改变业务状态。网络故障、API 超时、404、用户拒绝签名和合约回滚都会显示不同的错误或重试界面。

### 8.3 部署

系统采用前后端分离的部署方式，并将前端和后端分别部署在自有云服务器上。前端执行 `npm ci && npm run build` 生成 `dist` 静态资源，由 Nginx 对外提供页面访问和 SPA 路由回退；后端作为独立 Python 服务运行，通过 Gunicorn 启动 `run:app`。Nginx 将同一域名下的 `/api` 请求反向代理到后端服务，因此浏览器无需直接访问后端监听端口，也避免了跨域配置对主要部署环境的影响。前端通过环境变量注入 Sepolia 合约地址，合约 ABI 随前端源码一同构建。系统统一通过 <https://escrow.wuziran.fun/> 对外提供访问。

**访问方式：** 建议优先使用部署在自有云服务器上的主站 <https://escrow.wuziran.fun/>。项目同时保留 Render 备用版本，前端地址为 <https://freelance-escrow-front.onrender.com>，后端地址为 <https://freelance-escrow-api.onrender.com>。备用后端长时间无请求时可能进入休眠状态；若备用前端首次加载时无法取得数据，可先访问 <https://freelance-escrow-api.onrender.com/api/escrows?page_size=1> 唤醒后端服务，待服务启动后再刷新前端页面。

### 9.4 结果评价

各功能模块的正常流程能够完成，非法输入、越权操作和重复付款会被前端验证或智能合约拒绝。链上状态变化能够同步到项目详情、Dashboard 和交易历史，桌面端与移动端均可完成主要操作。当前测试以人工端到端测试和功能状态检查为主；缺少自动化合约与 API 测试，是测试完整性上的主要不足。

## 10. 遇到的挑战（Challenges Encountered）

1. **链上与链下状态同步。** 一笔金融交易可能已上链但后端写入失败，因此不能将两个步骤视为同一原子事务。本项目以链上结果为准并单独提示同步失败，但仍需要更可靠的补偿机制。
2. **角色和状态组合复杂。** 同一用户在不同项目中可能是客户、自由职业者或仲裁者；同一按钮还取决于项目和里程碑状态。实现时将角色推导和状态判断集中在详情页，减少错误操作入口。
3. **精确处理 ETH 金额。** JavaScript 浮点数不适合金融金额。项目在前端使用 `parseEther` 和 `BigInt`，接口及数据库使用 wei 字符串，从而避免精度丢失。
4. **移动端布局。** MetaMask 内置浏览器的宽度和可用高度较小，桌面表格及侧边导航并不适用。因此移动端改为底部导航、交易卡片、两列统计卡片和纵向操作按钮，并考虑安全区。

## 11. 局限性（Limitations）

- 后端目前信任前端提交的“交易已确认”数据，没有自行通过 RPC 校验交易哈希、发送者、事件和合约地址，也没有持续监听链上事件。因此数据库镜像可能遗漏交易或被伪造请求污染，但这不会改变链上资金。

- 合约采用单一指定仲裁者，争议处理仍包含对该地址的信任。仲裁者若离线或拒绝处理，争议资金可能长期锁定。

- 里程碑描述直接写入链上，数量多或文本长时 gas 成本较高，且公开链上的内容无法删除。
- 交易历史只在确认后写入，因此界面虽然保留 `PENDING` 筛选项，当前后端并不持久化 pending 交易。
- 区块链地址和交易记录是公开且可关联的，系统只能提供假名性，不能承诺隐私或匿名性。

## 12. 未来改进（Future Improvements）

1. 增加后端链上索引器：监听合约事件、按区块断点续扫，并对前端上报的交易回执进行 RPC 验证。
2. 将资金领取改为 Pull Payment，并评估 OpenZeppelin `ReentrancyGuard`、暂停机制和紧急恢复策略。
3. 引入多签或去中心化仲裁服务，并设计仲裁者超时与替换机制，避免争议永久锁定。
4. 将长文本移至 IPFS 或后端，仅在链上保存内容哈希，以降低 gas 并验证内容完整性。
5. 实现交易 pending 状态、失败交易记录、后端重试队列和链上/链下差异修复界面。

## 13. 结论（Conclusion）

本项目完成了一个面向真实金融信任问题的全栈 DApp。系统并非仅在网页中调用转账，而是通过智能合约建立了里程碑状态机、角色权限、托管资金、争议仲裁和超时退款规则。React 与 MetaMask 为用户提供可操作的 Web3 体验，Flask 与 SQLite 则补充了链上系统不擅长的元数据查询和交易索引能力。

实际记录表明，系统已在 Sepolia 上完成从创建、入金、提交到争议裁决和最终放款的完整流程。其主要价值在于把支付条件从中心化平台的内部规则转化为公开可验证的代码，同时保持私钥由用户控制。当前实现在线下索引可信度、数据库持久化、自动化测试、仲裁去中心化和 gas 优化方面仍有改进空间；这些限制也说明，构建可靠金融 DApp 不仅需要智能合约，还需要严谨处理前端体验、后端一致性、安全验证和运维部署。
