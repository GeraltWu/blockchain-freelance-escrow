
> **设计并开发一个原创的 Financial DApp，用 Blockchain + Smart Contract + Web Application 去解决一个现实中的金融问题。**

老师明确要求它既要有现实问题背景，又要真正实现一个可以操作的 DApp。

如果我们继续沿用前面讨论的 **Escrow Payment**，我建议把它设计成：

# Blockchain-Based Milestone Escrow for Freelance Payments

中文可以叫：

> **基于区块链的自由职业里程碑托管支付系统**

它不是简单的“转账系统”，而是解决：

> **客户和自由职业者在交易过程中互不信任，如何保证钱和服务按照约定条件交换？**

# 一、先把整个项目想象成一个真实产品

假设有两个人：

### Client

需要找人开发一个网站。

预算：

> 1 ETH

### Freelancer

愿意开发网站，但担心：

> “我做完以后，客户不给我钱怎么办？”

Client 又担心：

> “如果我先给钱，Freelancer 拿钱跑路怎么办？”

传统解决方案是找一个第三方平台：

```text
Client
   │
   │ Payment
   ▼
Centralized Platform
   │
   │ Payment
   ▼
Freelancer
```

你的项目尝试把**资金托管和条件式支付**这一部分放到 Smart Contract：

```text
             Blockchain
                  │
          ┌───────▼────────┐
Client ──►│ Escrow Contract │◄── Freelancer
          └───────┬────────┘
                  │
             Locked Funds
```

Client 的钱不是直接给 Freelancer，而是先进入 Smart Contract。

只有满足预先定义的条件，Contract 才允许资金释放。

---

# 二、但是为什么要做“Milestone”？

这是我建议你不要只做普通 Escrow 的关键。

真实的软件开发项目通常不是：

> 开始 → 做完 → 一次性付款

而是：

```text
Project
   │
   ├── Milestone 1
   │      UI Design
   │      $100
   │
   ├── Milestone 2
   │      Frontend
   │      $200
   │
   └── Milestone 3
          Backend
          $300
```

所以我们把 1 个项目拆成多个阶段。

例如总价：

> 1 ETH

可以：

| Milestone | 工作        |      金额 |
| --------- | --------- | ------: |
| M1        | UI Design | 0.2 ETH |
| M2        | Frontend  | 0.3 ETH |
| M3        | Backend   | 0.5 ETH |

Client 可以一次性把资金存入 Escrow Contract。

然后：

```text
M1完成
 ↓
Client批准
 ↓
0.2 ETH → Freelancer

M2完成
 ↓
Client批准
 ↓
0.3 ETH → Freelancer

M3完成
 ↓
Client批准
 ↓
0.5 ETH → Freelancer
```

这会让你的 Smart Contract 有比较明确的**状态机（state machine）**。

# 四、项目到底需要哪些角色？

我建议：

## Role 1：Client

客户。

可以：

* 创建 Escrow
* 设置项目金额
* 设置 Milestone
* 存入资金
* 查看项目状态
* Approve Milestone
* 发起 Dispute

## Role 2：Freelancer

自由职业者。

可以：

* 查看分配给自己的项目
* 查看 Milestone
* 提交 Milestone
* 查看付款
* 查看交易历史

## Role 3：Arbitrator

这个角色可以作为**可选角色**。

主要处理：

> Client 和 Freelancer 发生争议怎么办？

例如：

```text
Client
   │
   │ Dispute
   ▼
Arbitrator
   │
   ├── Release to Freelancer
   │
   └── Refund to Client
```

但是我要强调：

> **Arbitrator 不一定需要作为完整独立用户系统实现。**

个人项目规模有限，你可以把它做成一个简单的授权地址——由 Client 在创建项目时指定的第三方地址（双方线下协商好，每个项目可以不同），不必做成完整的独立用户系统。详见 data-model.md 1.5 仲裁机制说明。

# 七、Smart Contract 的核心 Functions

我建议控制在大约 **6–8 个核心函数**。

## 1. createEscrow()

Client 创建项目。

```text
Client
 ↓
createEscrow()
 ↓
Escrow Created
```

---

## 2. fundEscrow()

Client 把 ETH 存入 Contract。

```text
Client
 ↓
0.5 ETH
 ↓
Escrow Contract
```

---

## 3. submitMilestone()

Freelancer 表示某阶段已经完成。

```text
Freelancer
 ↓
submitMilestone()
 ↓
Milestone = SUBMITTED
```

---

## 4. approveMilestone()

Client 审核。

```text
Client
 ↓
approveMilestone()
 ↓
Milestone = APPROVED
 ↓
Payment Released
```

---

## 5. raiseDispute()

如果双方发生问题：

```text
Client / Freelancer
 ↓
raiseDispute()
 ↓
Milestone = DISPUTED
```

---

## 6. resolveDispute()

Arbitrator 处理。

```text
Arbitrator
 ↓
resolveDispute()
 ↓
Refund OR Release
```

---

## 7. refund()

在满足退款条件时退还 Client。

---

## 8. withdraw / releasePayment()

释放相应资金。

# 八、这里最重要的是“状态”

你的项目不是简单地：

```text
sendMoney()
```

而应该有状态变化。

例如：

```text
CREATED
   ↓
FUNDED
   ↓
SUBMITTED
   ↓
APPROVED
   ↓
RELEASED
```

如果发生问题：

```text
SUBMITTED
   ↓
DISPUTED
   ↓
RESOLVED
   ↓
RELEASED / REFUNDED
```

这就是一个非常好的 Smart Contract 业务逻辑。

# 十七、Validation 应该在哪里做？

老师明确要求：

> Input validation and error handling。

我建议做**双层验证**。

### Frontend validation

例如：

```text
Freelancer Address
不能为空

Amount
必须 > 0

Deadline
必须是未来时间

Milestone Amount
总和必须 = Total Amount
```

---

### Smart Contract validation

Contract 也不能相信 Frontend。

例如：

```solidity
require(msg.sender == escrow.client);
require(amount > 0);
require(block.timestamp < deadline);
require(milestone.status == SUBMITTED);
```

这就是比较标准的 Web3 安全思维：

> **Never trust the frontend.**

# 十八、Security 是这个项目非常重要的一部分

老师明确列出了：

* Authentication / Authorization
* Input validation
* Smart contract vulnerabilities
* Private key protection
* Gas optimization
* Data privacy / ethics。

所以至少应该考虑：

### 1. Access Control

Client 不能执行 Freelancer 的操作。

例如：

```text
Client
✓ approveMilestone()

Freelancer
✓ submitMilestone()

Arbitrator
✓ resolveDispute()
```

---

### 2. Reentrancy

涉及 ETH 转账时，需要考虑：

> Reentrancy Attack

---

### 3. Integer / amount validation

例如：

```text
Milestone total ≠ Escrow total
```

必须拒绝。

---

### 4. Double Release

不能：

```text
Approve
↓
Release
↓
Release again
```

否则会出现资金安全问题。

---

### 5. Private Key

**绝对不能把用户 Private Key 存在你的 Backend。**

用户通过 MetaMask 签名。

# 二十二、最重要的是：这个项目到底“解决什么问题”？

我们现在可以把它压缩成一个非常清楚的问题：

> **在跨境自由职业交易中，Client 担心 Freelancer 不交付，Freelancer 担心 Client 不付款。传统平台通过中心化托管机制降低这种风险，但用户需要依赖平台管理资金和执行付款规则。该项目探索使用 Ethereum Smart Contract 实现基于里程碑的资金托管和条件式付款，从而让预定义的支付规则以透明、可验证和自动执行的方式运行。**

注意这里的措辞：

**不是说 Blockchain 可以解决所有 freelance payment problems。**

而是：

> **我们选择其中一个非常明确的问题——conditional payment / escrow——用 Blockchain 做一个 prototype。**

这会让你的项目定位非常稳。
